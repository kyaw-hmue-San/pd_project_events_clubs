# 08 — Adversarial Architecture Stress Test

## Events & Clubs

**Architecture:** React + Vite → Express on Vercel → Supabase Auth/PostgreSQL  
**Purpose:** Identify failure modes before implementation and verify that mitigations are testable.

---

## 1. Weaknesses

| ID | Scenario | Expected invariant | How the system could fail | Impact | Likelihood | Severity | Recommended test |
|---|---|---|---|---|---|---|---|
| ST-01 | Two registration requests arrive simultaneously | At most one active registration exists per student and activity | Both requests pass an application-level pre-check before either writes | Duplicate registration and misleading confirmation | Medium | High | Fire concurrent requests and assert one success, one `409`, and one active row |
| ST-02 | A registration succeeds but the response is lost | Retrying must not create another active row | The client reports failure and repeats the operation blindly | Confusing UI or duplicate attempt | Medium | High | Drop the first response, retry, then fetch authoritative state |
| ST-03 | Cancellation is sent repeatedly | One record remains cancelled and history is preserved | Multiple updates create inconsistent timestamps or a later request fails confusingly | Incorrect status and poor recovery | Medium | Medium | Repeat the cancellation request and assert the same final state |
| ST-04 | Student changes a role value in the browser | The server trusts only protected role data | API accepts a client-supplied `ORGANIZER` role | Unauthorized activity management and data exposure | Medium | Critical | Modify request payload/token claims and attempt organizer endpoints |
| ST-05 | Organizer requests another organizer's activity registrations | Ownership is enforced for every private resource | Endpoint checks role but not activity ownership | Student registration data exposure | Medium | Critical | Use Organizer A's token against Organizer B's activity |
| ST-06 | A Supabase service-role key reaches the frontend | Privileged credentials remain server-side | Build-time environment configuration exposes the key | Full database access | Low | Critical | Scan built assets and repository history for privileged keys |
| ST-07 | Invalid activity fields are submitted | Invalid or incomplete data never becomes published | Frontend validates but a crafted API request bypasses it | Broken or misleading public activity | High | High | Call the API directly with missing and malicious fields |
| ST-08 | Database write fails during registration | No success is reported without a committed row | API sends success too early or performs partial work | User believes registration succeeded when it did not | Low | High | Inject a database failure and verify rollback plus error response |
| ST-09 | Supabase Auth is temporarily unavailable | Authentication is never bypassed | API accepts an unverifiable token or the UI loops indefinitely | Unauthorized access or unusable interface | Low | High | Simulate provider timeout and invalid verification response |
| ST-10 | A free Supabase project is paused before a demonstration | The team can restore service before the event | No pre-demo check exists | Demonstration outage | Medium | High | Run the release checklist several days and again one hour before demo |
| ST-11 | Vercel Function starts cold or runs in a new instance | Requests do not depend on process memory | Sessions, role state, or pending work are stored in memory | Intermittent authorization or state loss | Medium | High | Execute requests across fresh instances and verify stateless behavior |
| ST-12 | Activity status changes while a student is registering | Registration respects the committed activity state | Registration succeeds after activity becomes `CLOSED` | Invalid registration | Medium | High | Race close and registration requests in a transaction-focused test |
| ST-13 | Student enumerates sequential IDs | Private resources are protected regardless of identifier knowledge | Predictable IDs expose other registrations | Personal-data disclosure | Medium | High | Iterate known IDs with a Student token and verify `403`/`404` behavior |
| ST-14 | Logs capture tokens or personal data | Logs contain only sanitized diagnostics | Middleware logs authorization headers or full request bodies | Credential or privacy exposure | Medium | High | Inspect logs generated by authentication and validation failures |
| ST-15 | Malicious text is stored in an activity | Stored content remains inert when rendered | Unsafe HTML is rendered by the frontend | Cross-site scripting against students | Medium | High | Store script-like input and verify escaped rendering plus validation |
| ST-16 | Activity list is empty or the network is slow | The interface presents a clear recoverable state | Blank screen looks like a defect | Confusion and abandonment | High | Medium | Test loading, empty, timeout, offline, and retry states |
| ST-17 | Free-tier conditions change | Deployment remains within 0 THB or the team changes provider/plan | Old pricing assumptions are copied forward | Budget violation or outage | Medium | High | Recheck official plan terms at stack lock and release time |

## 2. Mitigations

### Registration Integrity

- Enforce an active-only unique index at the PostgreSQL boundary.
- Check activity state and insert the registration in one atomic operation.
- Map uniqueness conflicts to `409 Conflict`.
- Fetch current registration state after an ambiguous network outcome.

### Authentication and Authorization

- Verify Supabase access tokens in Express.
- Load trusted roles from protected server-side data or protected claims.
- Check role and resource ownership for every protected endpoint.
- Keep the service-role key server-side and apply database policies as defense in depth.

### Validation and Privacy

- Validate type, length, format, and controlled values in the API.
- Escape untrusted content when rendering.
- Return user-safe errors and sanitize logs.
- Store only the personal data required by the confirmed workflow.

### Runtime and Recovery

- Keep the Vercel API stateless.
- Do not depend on local disk, in-memory sessions, or background workers.
- Treat cancellation as an idempotent state transition.
- Roll back failed database operations and never report success early.
- Test the deployed system rather than relying only on local development.

### Cost and Demonstration Readiness

- Recheck Vercel and Supabase terms before deployment.
- Monitor quota use during testing.
- Confirm the Supabase project is active before demonstrations.
- Maintain an export or migration procedure for essential schema and test data.

---

## 3. Required Test Gate

The architecture cannot move from `READY WITH CHANGES` to `READY` until:

- [ ] ST-01, ST-04, ST-05, ST-06, ST-08, ST-11, and ST-12 pass automated integration tests.
- [ ] API validation and stored-XSS tests pass.
- [ ] Logs are inspected for secrets and unnecessary personal data.
- [ ] Loading, empty, offline, denied, and retry states are manually verified.
- [ ] Production frontend and API routes pass a smoke test on Vercel.
- [ ] Current free-tier conditions are recorded with a verification date.

---

## 4. Stress-Test Result

**Result: READY WITH CHANGES**

The design has no unavoidable architectural blocker, but implementation must prove the database, authorization, stateless-runtime, and failure-recovery invariants above. Documentation alone is not evidence that these protections work.
