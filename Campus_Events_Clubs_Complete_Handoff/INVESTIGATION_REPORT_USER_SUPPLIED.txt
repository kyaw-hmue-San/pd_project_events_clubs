**Assessment**

This is a documentation-heavy university project with a real Firebase backend and Assignment 5 integration work, but not a complete student-facing application. The repository has two different architecture directions, and there is not enough assignment-specific information to safely choose one for the final submission.

**1. Project Overview**

The intended product, Campus Events & Clubs, lets Students browse campus activities, view details, register, and cancel. Organizers create and publish activities and manage registrations. Those flows and the MVP boundary are defined in the PRD and requirements. The user-problem document correctly labels its pain points and current workflow as assumptions, not validated findings.

**2. Architecture and How It Relates**

- The main product documents choose **React + Vite, Express, Supabase Auth/PostgreSQL, and Vercel**. The canonical architecture, platform diagram, and README describe this direction.
- The separate Assignment 3 track chooses **Firebase Authentication, Express, and Firestore**. The Firebase assignment and database assignment explicitly say this implementation does not rewrite the earlier Supabase submissions.
- Assignment 5 extends the Firebase API with Team 10’s maintenance-platform integration. Its handoff and evidence report document provider API, webhook, retry, and degradation scenarios.
- Therefore, this is **not one system that has already migrated**. Supabase/Vercel is the product architecture in the main design; Firebase/Render is the implemented API and integration track.

**Provisional recommendation:** preserve Firebase for work specifically required by Assignments 3 and 5, since it is the only implemented backend. Do not port it to Supabase or combine both stacks yet. Whether the final product must use Supabase depends on the lecturer’s current implementation brief, which is not included here.

**5. Technical Issues to Resolve**

- **Lifecycle behavior differs from the PRD.** The PRD says `CLOSED` activities remain visible and cannot be reopened. The API lists only `PUBLISHED` activities and hides non-published activities from students; its update logic also allows `CLOSED → PUBLISHED`. Compare `PRD.md:379` with `api.mjs:102`, `api.mjs:117`, and `api.mjs:132`.
- **Cancellation API contracts differ.** The PRD documents `PATCH /api/registrations/:id/cancel`; Firebase implements `PATCH /api/registrations/:id` with `{"status":"CANCELLED"}`. Align the frontend, Postman collection, and final contract before integration.
- **The API has no CORS configuration.** The `DEPLOY.md:108` explicitly says browser calls from a different origin need it. A Vercel-hosted frontend cannot call the Render API reliably until allowed origins and preflight requests are configured.
- **Runtime models differ.** Firebase starts a persistent Express listener and an interval worker in `api.mjs:221`; the worker retries webhooks and partner requests in `integration.mjs:195`. That is designed for a persistent host such as Render, not the stateless Vercel Function described by the main architecture. Moving it as-is would break or undermine background retries.
- **Integration logs deserve tighter access.** Any authenticated Organizer can read `/api/integration/logs`; logs can include partner payloads and responses. See `api.mjs:95` and `integration.mjs:129`. Restrict access or redact/partition data before treating this as production-ready.
- Registration lists are capped at 50 without pagination, which the Firebase assignment itself acknowledges. The partner webhook retry loop also has no maximum attempt count.
- I did not use private credentials or write to Firebase. Consequently, current authenticated CRUD, deployed indexes, and live database permissions remain unverified.
